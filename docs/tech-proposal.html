局域网实时弹幕系统
LAN Danmaku Overlay

版本 v0.1（草案）　·　日期 2026-09-15　·　状态：待评审　·　下一步：确认第 8 节决策项后进入 M1

0. 一句话立项

做一个跑在局域网里的"弹幕大屏"：一台电脑启动 App 后自动开设房间并把弹幕层悬浮在桌面最上方，同一 WiFi 下的任何人用手机扫码就能发弹幕，弹幕从右往左滚动掠过屏幕顶部——不遮挡操作、不依赖外网、不装任何客户端。

核心设计取舍

把"发送"做成浏览器网页而不是客户端，是这个方案体验分最高的一步。用户零安装、跨 iOS/Android/Windows/Mac，成本全压在主机端一次开发上。

2. 系统架构

2.1 角色划分

角色载体职责
Host 主机桌面 App启动 HTTP + WebSocket 服务、维护房间状态、渲染弹幕层、托盘控制
Sender 发送端浏览器（手机/电脑）扫码打开页面，输入内容发送；纯前端，无本地依赖
Viewer 弹幕屏
P2		桌面 App（其他机器）加入已有房间，只接收并渲染，不发送

2.2 数据流

  1. 主机启动 → 枚举网卡 IPv4 → 挑出私有地址（192.168.x / 10.x / 172.16-31.x）
  2. 在端口 7321（占用则递增）上同时监听 HTTP 静态页 和 WebSocket 升级
  3. 把 http://192.168.1.23:7321 渲染成二维码显示在屏幕上
  4. 手机扫码 → 加载发送页 → 建立 WS 连接 → 发送 hello 握手
  5. 用户点击发送 → 客户端发 send → 服务端校验 + 限流 → 广播 danmaku 给所有连接（含主机自己）
  6. 主机弹幕层收到 → 分配轨道 → 创建 DOM 节点 → CSS 动画从右往左滚出 → 动画结束回收节点

2.3 房间模式

MVP 采用 单一默认房间（room: "default"），协议层预留 room 字段，后续做多房间不需要改协议。不做 P2P/去中心化——局域网里"找一台机器当中心"永远比"让 N 台机器互相同步"简单可靠。

3. 技术选型

3.1 桌面外壳选型 核心决策

这是整个项目唯一需要慎重拍板的点，因为它决定了开发难度、包体积和"能不能做出丝滑滚动"。

方案透明 + 穿透窗口弹幕动画包体积冷启动开发效率风险
Electron
推荐		 transparent + setIgnoreMouseEvents，两行 API CSS transform，GPU 合成层，最省事 90–120MB~1.5s高低
Tauri v2 支持，但穿透需 Rust 侧调 Win32 API 同样是 WebView，渲染效果一致 8–15MB~0.5s中中高（Rust 门槛）
PySide6 (Qt) 三段式设置：无边框 + 半透明背景 + 鼠标透明 QPropertyAnimation / QGraphicsScene，滚动弹幕实现较费劲 60–80MB~2s中中
C# WPF AllowsTransparency + WS_EX_TRANSPARENT Storyboard 动画，性能好 40–70MB~1s中高（跨平台差）
结论：主推 Electron

1. 弹幕的本质是"让一批文字在屏幕上丝滑移动"，这正是浏览器渲染引擎最擅长的场景——CSS transform 走 GPU 合成层，60fps 稳定，不用自己写动画调度器。
2. 透明 + 置顶 + 点击穿透在 Electron 上是成熟 API，完全不用碰平台原生代码。
3. 服务端 Node.js 与 Electron 同进程，前后端一套语言、一个打包产物，省掉跨语言 IPC。
4. 发送端页面 100% 复用同一套前端技术栈，手机端适配成本极低。

付出的代价：安装包约 100MB。局域网内分发（U 盘 / 内网共享）可以接受。

什么时候该换方案：

  • 如果硬性要求 ≤15MB 或要跑在低配机器上 → 换 Tauri v2
  • 如果目的是顺便练 Python 桌面开发（和自己转大模型的技术栈统一）→ 换 PySide6，服务端用 FastAPI + websockets，也是完整一套

3.2 弹幕渲染引擎

方案优点缺点定位
DOM + CSS 动画
MVP 采用		 文字样式完全自由（颜色/描边/emoji），GPU 合成层，代码量小 同屏 300+ 条时 DOM 节点压力显现 MVP 主力
Canvas 2D 几千条也不掉帧，完全可控 要自己 measureText、处理 emoji、逐帧重绘 v0.3 按需切换

做法：抽象一个 DanmakuRenderer 接口，MVP 用 DOM 实现，将来换 Canvas 只替换实现类，轨道调度逻辑复用。

轨道调度算法

  1. 把弹幕带按行高切成 N 条轨道（行高 = 字号 × 1.6）
  2. 新弹幕优先选择"最后一条弹幕右边缘最早离开屏幕"的轨道
  3. 能否塞入的判定：轨道内末条弹幕的右边缘已离开屏幕右侧，或两者速度差不足以追尾
  4. 所有轨道都满 → 复用最早可用的轨道（允许重叠）或短暂排队
  5. 宽度预测量用 canvas.measureText，绝不用字符数估算——中英文 emoji 混排下估算必然翻车

3.3 通信协议

选型：原生 WebSocket（服务端 ws 库）

  • 为什么不 SSE：SSE 只能服务端单向推送，发弹幕还得另开 HTTP POST，两套通道，不值当
  • 为什么不用 UDP 广播：不可靠且无顺序，弹幕丢一条用户能看出来；UDP 只适合用来做局域网发现
  • 为什么不用 Socket.IO：它的 room 和自动重连确实开箱即用，但包体积大、协议私有。局域网环境下 WebSocket 必然连通，自己写心跳 + 重连不过几十行，更轻更可控

3.4 局域网接入与发现

方式体验实现成本优先级
屏幕二维码 + IP 提示扫码即用，0 输入低（qrcode 库）MVP 必做
手输 IP 网址一般，适合扫码不便的场景无MVP 附带
mDNS / Bonjour 广播App 内可直接发现房间，免输 IP中（bonjour-service）P1
必须提前处理：Windows 防火墙

首次监听端口时 Windows 会弹防火墙确认框，用户点"取消"或选了"公用网络"就会导致手机完全连不上，而 App 看起来一切正常——这是这类项目最容易踩的坑。对策：启动后主动做一次本机端口可达性自检，失败时在界面上显示醒目横幅 + 一键跳转防火墙设置，而不是静默失败。

4. 关键技术难点与对策

风险影响对策
Windows 防火墙拦截端口手机连不上，功能直接不可用且难以自查启动时端口可达性自检；失败给出横幅提示 + 一键跳转防火墙设置
点击穿透在个别系统版本异常弹幕层挡住鼠标，用户无法操作默认开启穿透；托盘提供"临时锁定鼠标"开关兜底
独占全屏应用（游戏/播放器）下无法覆盖弹幕看不见文档说明需使用无边框窗口/窗口化模式；检测到异常时提示
多显示器 + 高 DPI 缩放错位弹幕跑到别的屏、位置偏移用 Electron screen API 取 display.bounds 与 scaleFactor，按物理像素换算；设置页可选目标屏幕
刷屏导致卡顿掉帧主线程阻塞，滚动不流畅服务端限流 + 客户端队列上限 + 超限丢最旧 + DOM 节点池化复用
中英文 emoji 混排宽度计算错误轨道判断失准，弹幕互相重叠统一用 canvas.measureText 预测量，不靠字符数估算
macOS 全屏空间下不显示置顶失效level: 'screen-saver' + setVisibleOnAllWorkspaces(true)

5. 通信协议设计

客户端 → 服务端

{ "type": "hello",  "name": "小明", "room": "default" }
{ "type": "send",   "text": "666", "color": "#FFD400", "size": 24, "name": "小明", "ts": 1757900000000 }
{ "type": "ping" }

服务端 → 客户端

{ "type": "danmaku", "id": "uuid", "text": "666", "color": "#FFD400", "size": 24,
  "name": "小明", "mode": "scroll", "ts": 1757900000123 }
{ "type": "ack",    "id": "local-1", "ok": true }
{ "type": "reject", "code": "RATE_LIMIT", "msg": "发得太快了，歇一下" }
{ "type": "stats",  "online": 12 }
{ "type": "pong" }

控制消息（主机下发）

{ "type": "clear" }              // 清屏
{ "type": "pause" | "resume" }   // 暂停 / 恢复上屏
{ "type": "config", "fontSize": 24, "speed": 8, "lanes": 3, "heightRatio": 0.3 }

约束（服务端强校验，不信任客户端）

  • text 长度 ≤ 60 字，超出直接截断
  • color 只接受合法 hex 或预设白名单，防注入
  • size 统一 clamp 到 [16, 48]，防止超大字号撑爆屏幕
  • name 长度 ≤ 12 字，空白替换为"匿名"

8. 待决策事项

下面几条确认后就能直接开写 M1。

  1. 桌面外壳选哪个？ 推荐 Electron —— 弹幕丝滑动效最稳、坑最少。若想体积小选 Tauri；若想统一 Python 技术栈选 PySide6。
  2. 主要使用场景是什么？课堂 / 会议 / 直播 / 聚会 / 自己玩 这个决定要不要提前做审核模式和屏蔽词（正式场合几乎是刚需，聚会场景则是负担）。
  3. 发送端只做浏览器网页够吗？还是也需要一个桌面发送客户端？ 建议先只做网页，桌面客户端收益低。
  4. 要不要做 F14 的 AI 彩蛋？ 弹幕情感分类过滤 / 高光弹幕精选 —— 这条能和你转大模型的方向结合，可以当简历项目写。
