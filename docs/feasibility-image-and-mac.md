# 两个任务的可行性分析

> 结论速览
> - **图片发送**：技术上完全可行，与现有架构契合度高，MVP 约 1~2 天；主要工作量在"渲染层轨道适配"和"上传/存储/清理"。
> - **在 Windows 上做 Mac 版**：**写代码可以，出包不行**。Windows 无法编译/签名 macOS 安装包，必须借一台 Mac 或走 CI（GitHub Actions 的 macos runner）。代码侧适配量不大（约 0.5~1 天）。

---

## 一、图片发送功能

### 1. 现状约束（决定了方案怎么选）

| 现状 | 位置 | 影响 |
|---|---|---|
| WebSocket 单条消息上限 **4096 字节**（`MAX_WS_MESSAGE`） | `src/main/server.js:29` | 图片不能直接走弹幕消息通道 |
| 文本上限 60 字，服务端强校验 | `src/shared/protocol.js` `LIMITS.TEXT_MAX` | 图片需要一个独立的"体积约束"体系 |
| 弹幕渲染是纯文本（`textContent` + 按文字宽度算轨道） | `src/overlay/overlay.js:184-240` | 图片要改"宽度测量"和"轨道高度"逻辑 |
| HTTP 服务对静态资源有白名单前缀 | `src/main/server.js` `DEFAULT_ALLOWED_PREFIX` | 图片目录要加白名单，或走专门的读取接口 |
| 已有 `/api/*` 处理器注入点（公网模式管理接口在用） | `src/main/server.js:170` | 上传接口可复用这个入口，改动小 |
| 无任何数据库/文件存储，弹幕历史只在内存 | `main.js state.recent`、`room.js` | 图片得落盘，且要有清理策略 |

### 2. 两种传输方案

**方案 A：图片内容塞进弹幕消息（base64）**
- 需要把 `maxPayload` 从 4KB 抬到 1MB 以上，且每条弹幕都要走 WS 全量分发。
- 主机会把图片再广播给所有加入端 → N 倍流量；公网模式下直接把隧道打爆。
- 不利于缓存（同一张图重复发要重复传）。
- **不推荐**，只适合"极小分辨率缩略图"这种玩具场景。

**方案 B（推荐）：HTTP 上传 + 广播图片地址**
1. 发送端本地压缩（canvas 缩放 + webp/jpeg 编码，长边 ≤ 1280，质量 0.8，通常 50~200KB）
2. `POST /api/upload`（带房间口令/管理员 token）→ 服务器校验后落盘，返回 `{ id, url, w, h }`
3. 再发一条普通弹幕消息：`{ mode:'image', url:'/uploads/xxx.webp', w, h, text:'可选配文' }`
4. 各端渲染时用**地址**加载（同一张图只传一次，浏览器/Electron 自带缓存）

为什么这样最合适：弹幕协议本身不用改结构（只加一个 `mode`），图片分发复用了 HTTP 静态服务，公网模式下的隧道压力可控。

### 3. 需要动的模块（按改动量排序）

| 模块 | 工作内容 | 量级 |
|---|---|---|
| 发送端网页 `src/sender/` | 「+图片」按钮 / 拖拽 / Ctrl+V 粘贴、预览、可选配文、上传进度与失败重试、体积超限提示 | 中 |
| 服务端 `src/main/room.js` + `server.js` | `/api/upload`（magic bytes 校验 png/jpg/gif/webp、随机文件名、单文件上限、白名单目录、防路径穿越）；弹幕 `mode` 校验与广播；图片专用限流 | 中 |
| 弹幕层 `src/overlay/` | `img` 渲染；按协议给的 `w/h` 与本地字号比例换算显示尺寸；**轨道高度适配**（现在轨道高由字号决定，图片可能需要占 2~3 条轨道高度，或强制压缩到一条轨道）；预加载失败回退成 `[图片]` | 中（最需要调试） |
| 桌宠 `src/ball/` | 粘贴/选图发送（和文字弹幕共用发送链路） | 小 |
| 控制台 `src/control/` | 「允许图片」总开关、单文件体积上限、图片频率限制、最近弹幕列表显示缩略图 | 小 |
| 存储与清理 | 落盘目录（建议 `userData/uploads`）、按数量/总容量/时长的清理（如保留最近 200 张或 500MB）、退出时的策略选择 | 小 |
| 兼容与降级 | 老客户端收到 `mode:'image'` 不认识 → 回退显示 `[图片]`；纯文本端（如无 JS 场景）同样回退 | 小 |
| 测试 | `smoke-test.js` 加：上传成功/类型不符被拒/超限被拒/广播内容正确；E2E 截图验证图片确实上屏 | 小 |

### 4. 风险点（提前定策略就能规避）

1. **安全**：上传接口必须做类型嗅探（不能信扩展名/MIME）、随机文件名、大小与频率限制；公网模式下建议**默认关闭图片**，或仅管理员可发（`admin` 已有 token 机制）。
2. **性能**：一张 2MB 原图 × 20 台设备屏幕刷新会明显卡；靠"客户端压缩"从源头解决，服务器再兜底拒收超限文件。
3. **轨道布局**：这是唯一需要认真设计的渲染改动——现有 `laneHeight` 与字号强绑定，图片高度会破坏节奏；建议限制图片显示高度 ≤ 2 倍行高，超出按比例缩小。
4. **屏蔽词**：只能作用于配文，图片内容无法自动识别（除非引入 OCR/审核模型，不建议现在做）。
5. **存储膨胀**：必须有自动清理，否则长时间开房间会占满磁盘。
6. **暂停/清屏/CONFIG 广播**：图片弹幕走同一套 `publish` 流程，这些控制指令自动生效，无需额外处理。

### 5. 工作量估计（MVP）

- 服务端上传 + 校验 + 清理：0.5 天
- 发送端（含压缩）：0.5 天
- 弹幕层渲染与轨道适配：0.5 天（含调试）
- 控制台开关 + 端到端测试：0.5 天
- **合计 1.5~2 天**（不含"图片审核/OCR"这类扩展）

## 二、在 Windows 上开发 Mac 版

### 1. 硬性事实（先看清边界）

| 事项 | Windows 上能否完成 |
|---|---|
| 写/改 Mac 适配代码、配置、图标 | ✅ 能 |
| 跑 Electron 在 macOS 上的运行验证 | ❌ 不能（Windows 跑不了 macOS 二进制） |
| 用 electron-builder 打 `.dmg` / `.app` | ❌ **不能**（dmg 依赖 macOS 的 `hdiutil`，且签名必须在 macOS 上做） |
| 代码签名 / 公证（notarization） | ❌ 不能（需要 macOS + Apple 账号） |
| 生成 `.icns` 图标 | ⚠️ 不必自己转：electron-builder 会从 `build/icon.png` 自动生成（≥512×512，当前正好是 512，建议补一张 1024 更稳） |

**所以"在 Windows 上开发 Mac 版"的正确定义是：Windows 上完成全部代码与配置，出包与验收借 Mac。**

### 2. 出包途径对比

| 途径 | 成本 | 适合场景 | 限制 |
|---|---|---|---|
| 朋友的 Mac（你已经在联系的那位） | 0 | 出包 + 真机验收 | 需要他有 npm 环境；unsigned 包首次打开要右键→打开 |
| **GitHub Actions `macos-latest` runner** | 0（公开仓库免费额度充足） | 持续出包、每次改完自动构建 | 需要建仓库；签名需要 Apple 证书 secrets |
| 云 Mac（MacinCloud / MacStadium） | 约 ¥200~600/月 | 无 Mac 又要长期迭代 | 付费、远程操作 |
| 黑苹果 / macOS 虚拟机 | 0~低 | ❌ 不推荐 | 授权灰区、GPU/网络不稳定，出的包自测都不可信 |

推荐组合：**代码在 Windows 写 → GitHub Actions 自动出 unsigned dmg → 朋友的 Mac 上真机验收**。这样你全程不碰 Mac，也能最快速迭代。

### 3. 代码侧需要适配的清单（我已逐项对着现有代码看过）

| # | 事项 | 现状 | 需要做的事 | 量级 |
|---|---|---|---|---|
| 1 | 打包配置 | 只有 `host.yml / join.yml / all.yml`（win 目标） | 新增 `build/mac.yml`：`target: dmg + zip`、`category: public.app-category.social-networking`、`hardenedRuntime`、`entitlements`（局域网/网络权限）、`mac.icon` | 小 |
| 2 | 公网隧道 | `tunnel.js` 只找 `cloudflared.exe`、临时目录写死 `.exe` | 增加 darwin 二进制名（`cloudflared-darwin-arm64/amd64`）与 brew 安装路径；`which` 分支已兼容 | 小 |
| 3 | 托盘图标 | 用彩色 `assets/tray.png` | macOS 菜单栏要**单色 Template 图**（+@2x），否则在深/浅色菜单栏里很难看；新增 `tray-macTemplate.png` 并 `setTemplateImage(true)` | 小 |
| 4 | 托盘交互 | Windows 是"单击/双击打开窗口 + 右键菜单" | macOS 托盘单击默认展开菜单，需重新定义（点击展开菜单、菜单里"打开窗口"），并改掉界面文案里的"双击托盘"提示 | 小 |
| 5 | 应用菜单 | 现在没有自定义菜单（`autoHideMenuBar`） | macOS 关闭所有窗口后菜单栏仍是本应用，需要最小菜单（关于/退出/编辑/窗口），并保证 `Cmd+Q/Cmd+W` 行为符合 mac 习惯 | 小 |
| 6 | Dock 图标 | 无 | 决定是否 `app.dock.hide()`（纯托盘常驻）——建议**保留 Dock**，mac 用户更习惯；这点要你拍板 | 小 |
| 7 | 防火墙文案 | `main.js:1312` 有 `windowsdefender://` 深链，非 win32 只给一句提示 | macOS 换成「系统设置 → 网络 → 防火墙」；另需处理 **macOS 15 局域网权限弹窗**（`NSLocalNetworkUsageDescription` 写进 Info.plist，加入端自动发现会触发） | 小 |
| 8 | 全屏弹幕层 | 已用 `setVisibleOnAllWorkspaces(true,{visibleOnFullScreen:true})` + `screen-saver` 层级 | 需在 Mac 上实测（覆盖全屏应用、多 Space、刘海/菜单栏区域的坐标基准差异） | 中（需真机） |
| 9 | 多显示器坐标 | 用 `display.bounds` | macOS 坐标系原点在主屏左上、副屏可为负值，需实测校准 | 小 |
| 10 | 桌宠透明窗口 | 已关 GPU 加速 + 无边框透明 + `alwaysOnTop` | 一般可直接用；需实测拖动、`acceptFirstMouse`、点击穿透 | 小 |
| 11 | 字体 | CSS 已含 `"PingFang SC"` 回退 | 基本不用改，实测中文/emoji 渲染即可 | 小 |
| 12 | 便携版概念 | win 有 portable target | macOS 无便携版；改成 dmg（拖拽安装）+ zip | 小 |
| 13 | 签名/公证 | 无 | 不买 Apple 开发者账号（$99/年）：用户首次打开需右键→打开，或 `xattr -dr com.apple.quarantine /Applications/xxx.app`。要"双击无警告"就得买账号 + 公证流程 | 小（但需决策） |

### 4. Mac 上的验收方式（重要）

项目**没有任何原生依赖**（`ws`、`qrcode` 都是纯 JS），所以现有的测试资产可以**直接在 Mac 上复用**：

- `node scripts/smoke-test.js`（71 项服务端/协议回归）
- `node scripts/smoke-public.js`（公网模式）
- E2E 脚本（CDP 驱动真实 Electron 窗口）——跨平台可用

也就是说：**Mac 上能否跑通 = 一句话验证**，不需要重写测试。这会让 Mac 版的风险显著低于一般跨平台移植。

### 5. 工作量与风险

- Windows 侧（可以现在就做完）：Mac 打包配置 + 上述 12 项代码适配 + 生成 tray 模板图 + 写 CI workflow ≈ **0.5~1 天**
- Mac 侧（朋友或 CI）：出包 + 真机验收 + 3~5 处实测微调（全屏层、托盘、多屏坐标）≈ **0.5 天 + 若干轮反馈**
- 主要风险集中在：**全屏弹幕层在多 Space / 全屏应用下的表现**、**macOS 15 局域网权限弹窗**、**Gatekeeper 首次打开体验**。三者都需要真机确认，无法在 Windows 上预判。

## 三、建议的推进顺序

1. **先做 Mac 版（不含图片）**：改动集中在打包配置和几处平台分支，风险低、能最快拿到"能在 Mac 上跑"的成果；朋友的 Mac 一旦跑通，后面所有改动都能顺带验证。
2. **再做图片发送**：功能改动面大（协议 + 上传 + 渲染 + UI），放在一个已有 Mac 验证链路的版本上做，避免一次引入两类问题。
3. 如果两件一起做，建议把图片功能做成**可开关的实验特性**（控制台默认关），先在 Windows 上跑通再开。
